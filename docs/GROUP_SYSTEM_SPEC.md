# MosaicVPN — Спецификация системы групп

**Версия:** 1.0
**Статус:** на реализацию
**Связанные документы:** `PRD_v0.3.0.md`, `PLAN_v0.3.0.md`

---

## 1. Зачем переделываем

Текущая система групп нерабочая с точки зрения пользователя:

1. Группы приходят **только** внутри `GET /v1/manifest`. Если провайдер не отдал
   манифест — вкладка пустая, и пользователь видит нерабочий раздел.
2. Списка групп в API нет: есть `/v1/groups/{id}/select` и `/v1/groups/{id}/health`,
   но нет `GET /v1/groups`. Клиенту неоткуда взять перечень.
3. Сущность размазана по двум вкладкам — `Subscriptions` и `Groups`.
4. Архитектурно трафик идёт `клиент → наш сервер → сервер из пула`, что грузит наш
   сервер вдвое без выигрыша для пользователя.

---

## 2. Целевая архитектура

### 2.1 Ключевое решение: наш сервер уходит из пути трафика

**Было:**
```
клиент ──▶ наш сервер ──▶ узел из free-пула ──▶ интернет
           (двойная нагрузка, наш трафик = трафик всех клиентов)
```

**Стало:**
```
                 ┌── координация (только метаданные, ~килобайты) ──┐
клиент ─────────▶│  наш сервер: список узлов, health, назначение   │
                 └────────────────────────────────────────────────┘
клиент ──────────────────▶ узел из free-пула ──────────────▶ интернет
                           (весь трафик, наш сервер не участвует)

аварийный режим:
клиент ──▶ наш узел (единственный, только когда пул недоступен)
```

Наш сервер отдаёт только метаданные: перечень узлов, их состояние и рекомендацию,
к какому подключиться. Пользовательский трафик через него не идёт.

### 2.2 Три источника узлов

| Источник | Приоритет | Назначение |
|---|---|---|
| `pool` | 1 | Публичные бесплатные узлы, собранные с внешних источников по HTTPS |
| `user` | 2 | Подписки, добавленные самим пользователем |
| `emergency` | 3 | Один наш узел, включается когда пул пуст или мёртв |

## 3. Модель данных

### 3.1 Группа

```go
// ServerGroup — единица выбора для пользователя.
type ServerGroup struct {
    ID          string       `json:"id"`
    Title       string       `json:"title"`
    Source      GroupSource  `json:"source"`      // pool | user | emergency
    Strategy    GroupStrategy `json:"strategy"`   // см. 4
    Criterion   GroupCriterion `json:"criterion"` // см. 3.3
    Nodes       []NodeRef    `json:"nodes"`
    RequiredTier UserTier    `json:"required_tier,omitempty"`

    // health
    PingInterval  int `json:"ping_interval"`   // сек, по умолчанию 30
    MaxRetries    int `json:"max_retries"`     // по умолчанию 3
    FailoverDelay int `json:"failover_delay"`  // сек, по умолчанию 2

    // отображение
    Badge       string `json:"badge,omitempty"`
    Description string `json:"description,omitempty"`
    Icon        string `json:"icon,omitempty"`
}
```

### 3.2 Узел с телеметрией загрузки

```go
type NodeRef struct {
    ServerID  string  `json:"server_id"`
    Weight    int     `json:"weight"`      // 1..100, статический вес
    Load      float64 `json:"load"`        // 0..1, текущая загрузка
    LatencyMs int     `json:"latency_ms"`  // последний замер
    Alive     bool    `json:"alive"`
    LastSeen  int64   `json:"last_seen"`   // unix
    Country   string  `json:"country,omitempty"`
    City      string  `json:"city,omitempty"`
}
```

### 3.3 Критерий выбора

Пользователь выбирает, **по какому признаку** группа подбирает узел:

| Критерий | Поведение |
|---|---|
| `auto` | Комбинированная оценка: загрузка + пинг (по умолчанию) |
| `min_ping` | Наименьшая задержка |
| `location` | Только узлы указанной страны (`criterion_value: "DE"`) |
| `min_load` | Наименее загруженный узел |
| `max_speed` | Наибольшая измеренная скорость |

## 4. Стратегии выбора

Четыре стратегии, три из которых уже есть в `internal/subs/pool.go` и переиспользуются.

### 4.1 `urltest` — по наименьшей задержке
Периодический замер, выбор минимального. Подходит для «просто работай».

### 4.2 `weighted_round_robin` — распределение по загрузке

**Это ключевая стратегия для free-пула.** Клиенты размазываются по узлам, чтобы ни
один не лёг под нагрузкой.

Формула оценки (меньше — лучше):

```
score = latency_ms / (weight × (1 - load))

где:
  latency_ms — последний замер задержки
  weight     — статический вес узла (1..100)
  load       — текущая загрузка 0..1

При load → 1 знаменатель → 0, score → ∞, узел перестаёт выбираться.
Защита: если load ≥ 0.95, узел исключается из выборки.
```

Пример на трёх узлах:

| Узел | latency | weight | load | score | выбор |
|---|---|---|---|---|---|
| A | 40 мс | 10 | 0.90 | 40/(10×0.1) = **40.0** | нет |
| B | 80 мс | 10 | 0.20 | 80/(10×0.8) = **10.0** | **да** |
| C | 60 мс | 5 | 0.50 | 60/(5×0.5) = **24.0** | нет |

Узел A быстрее всех, но перегружен — уходит на B. Это и есть распределение по
загруженности.

### 4.3 `fallback` — по порядку
Первый живой из списка. Порядок задаётся вручную.

### 4.4 `direct_node` — фиксированный узел
Без автовыбора. Используется для аварийного узла.

## 5. Пул бесплатных серверов

### 5.1 Требования к источникам

- **Только HTTPS.** Источник по `http://` отклоняется на этапе конфигурации.
- Источник описывается в конфиге, а не хардкодится.
- Каждый источник имеет таймаут и лимит на размер ответа.

```yaml
# config: pool_sources
pool_sources:
  - url: "https://example.org/sub.txt"
    format: auto        # auto | base64 | clash | singbox | sip008
    enabled: true
    trust: medium       # high | medium | low — влияет на стартовый weight
    timeout_sec: 15
    max_bytes: 2097152
```

### 5.2 Жизненный цикл узла

```
   ┌──────────┐  fetch    ┌───────────┐  health ok   ┌────────┐
   │ источник │──────────▶│  candidate│─────────────▶│  alive │
   └──────────┘           └───────────┘              └────────┘
                                │                         │
                          health fail                fail × MaxRetries
                                ▼                         ▼
                          ┌──────────┐              ┌──────────┐
                          │ rejected │              │   dead   │
                          └──────────┘              └──────────┘
                                                          │
                                                    retry через 10 мин
                                                          ▼
                                                    ┌───────────┐
                                                    │ candidate │
                                                    └───────────┘
```

### 5.3 Оценка загрузки

Точной загрузки чужого узла мы не знаем. Оцениваем косвенно:

1. **Собственные назначения.** Демон считает, сколько наших клиентов отправлено на
   узел за последние 5 минут → `assigned_load`.
2. **Деградация задержки.** Рост пинга относительно медианы узла → `latency_load`.
3. Итог: `load = clamp(0.6 × assigned_load + 0.4 × latency_load, 0, 1)`.

Это честная эвристика, а не выдуманная телеметрия. В UI показывается как
«загруженность», без претензии на точность до процента.

## 6. API

### 6.1 Новые эндпоинты

```
GET    /v1/groups                    список всех групп (pool + user + emergency)
GET    /v1/groups/{id}               одна группа с узлами и их состоянием
POST   /v1/groups                    создать пользовательскую группу
PATCH  /v1/groups/{id}               изменить (title, strategy, criterion)
DELETE /v1/groups/{id}               удалить пользовательскую
POST   /v1/groups/{id}/connect       выбрать узел по стратегии и подключиться
GET    /v1/pool/sources              список источников пула
POST   /v1/pool/refresh              принудительно обновить пул
GET    /v1/pool/stats                размер пула, живых, мёртвых
```

### 6.2 Существующие (сохраняются)

```
GET /v1/groups/{id}/select    выбрать узел без подключения
GET /v1/groups/{id}/health    состояние узлов группы
```

- Индикатор загрузки — цветом, не только числом.

## 9. Приоритет подключения

```
1. Пользователь выбрал группу явно      → используем её
2. Иначе последняя успешная группа      → используем её
3. Иначе pool-auto                      → выбор по загрузке
4. Пул пуст или все мертвы              → emergency
5. Emergency недоступен                 → честная ошибка с причиной
```

Молчаливого падения в неизвестное состояние быть не должно: на шаге 5 пользователь
видит текст ошибки и кнопку повтора.

---

## 10. Что переиспользуем

`internal/subs/pool.go` уже содержит рабочие реализации четырёх стратегий, включая
`weighted_round_robin` со схожей формулой. Переписывать с нуля не нужно —
расширяем: добавляем `load`, критерии и источники.

## 11. Критерии приёмки

| ID | Критерий |
|---|---|
| GS-1 | `GET /v1/groups` возвращает ≥ 5 групп по умолчанию на чистой установке |
| GS-2 | 10 подключений подряд распределены минимум по 3 разным узлам |
| GS-3 | Узел с `load ≥ 0.95` не выбирается ни разу за 100 итераций |
| GS-4 | При пустом пуле подключение уходит на `emergency` |
| GS-5 | Источник по `http://` отклоняется с явной ошибкой |
| GS-6 | В `app_shell.dart` ровно одна вкладка групп |
| GS-7 | Карточка группы не шире 520 px на любом разрешении |
