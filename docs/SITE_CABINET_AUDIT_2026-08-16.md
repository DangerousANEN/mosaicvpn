# MosaicVPN: аудит сайта и кабинета (16 августа 2026)

## Главная страница

Публичная страница `https://sub.zxc1x1.ru/` использует светлую «атласную» тему с сеткой и аккуратным hero-блоком. Однако разделы III («Возможности») и IV («Смарт-группы») оформлены как плотные технические карточки с emoji и внутренними терминами (`urltest`, `weighted_round_robin`, `direct_node`, WFP, SOCKS port). Это не соответствует задаче продающего сайта для обычного пользователя: преимущества не иерархизированы, а преимущества для провайдера смешаны с пользовательским сценарием.

Актуальная страница также продолжает ссылаться на release `v0.3.9` в download CTA, хотя последний подготовленный клиентский patch не опубликован. Это не меняется в рамках UI-redesign без отдельного release decision.

## Личный кабинет

Публичный `https://sub.zxc1x1.ru/cabinet.html` открывает страницу логина. В desktop viewport видны шапка, описание единого аккаунта и card login по Telegram `/link` коду. Разметка текущего authenticated кабинета находится в статичном HTML/JS и должна быть отдельно проверена/переработана.

Проблемы, требующие исправления:

1. Mobile layout не должен использовать desktop-table/column assumptions; после авторизации account summary, payment history, devices и actions должны стать one-column blocks.
2. Account ID пока не является ясным, копируемым элементом UI.
3. Нужен отдельный, строго server-side admin route с `is_admin` проверкой; обычный кабинет не должен получать admin controls или data.
4. Любое начисление баланса должно принимать account ID, положительную amount, обязательную reason, иметь session authorization, idempotency/confirmation и audit log с временем, администратором, target ID, суммой и основанием.

## Рекомендуемая информационная архитектура

Главная: hero → простые причины использовать сервис → как подключиться за три шага → прозрачная цена/доступ → технические возможности для продвинутых в раскрываемом/вторичном блоке.

Кабинет: mobile-first account card → быстрые действия (пополнить, заморозить, устройства) → статус доступа → платежи; Account ID рядом с профилем и copy control.

Админка: отдельная страница только после admin auth; поиск по account ID, сумма начисления в рублях/днях, reason и history table.

## Утверждённое решение для реализации

Раздел III будет заменён на **«Всё нужное — без сложных настроек»**: четыре bento-карточки с SVG-иконками вместо emoji и с пользовательскими ценностями — быстрое подключение, единый аккаунт, выбор сценария и понятный контроль доступа. Технические детали не будут выдаваться за главную ценность.

Раздел IV будет заменён на **«Маршрут под задачу, а не ручной выбор серверов»**. Пользователь увидит понятный путь из трёх шагов: выбрать задачу, получить автоматически подобранный маршрут, сохранить непрерывность подключения. Оригинальные внутренние стратегии (например, `urltest` и `weighted_round_robin`) останутся только в provider documentation, без отображения конкретных станций из общего пула.

Кабинет будет переписан как mobile-first single-column layout. Верхняя account card будет показывать копируемый **ID аккаунта**, nickname (если есть), состояние доступа и быстрые действия. Карточки, формы и payment history должны оставаться читабельными при ширине 320px; таблицы на mobile превратятся в semantic activity cards.

Кнопка «Администрирование» будет появляться только при `profile.is_admin === true`. Это лишь UX-условие; каждая серверная административная операция отдельно проверяет session token и `telegram_id in ADMIN_IDS`.

Серверная операция начисления получит account ID, целую положительную сумму в рублях (= дням доступа в действующей модели), обязательное основание и уникальный `request_id`. До обращения к subscription API backend создаст запись `processing` с уникальным ID; повторный запрос не начислит сумму второй раз. После успеха либо ошибки запись будет финализирована и доступна только администратору в журнале. UI сначала покажет browser confirmation с точным ID, суммой и основанием, затем выполнит запрос.

Сопутствующая корректировка: web cabinet будет принимать 8-символьные коды `/link`, потому что backend реально выпускает именно такие коды. Это устраняет существующее несоответствие `maxlength=6`.

## Визуальная проверка до публикации

Локальная desktop-проверка новой главной страницы подтверждает, что раздел III стал читаемой bento-композицией с выразительной тёмной основной карточкой и SVG-иконками. Раздел IV теперь объясняет логику групп простым языком, не выводя пользователю конкретные станции или внутренние стратегии распределения. Навигационный пункт обновлён на «Как работает».

Mobile screenshot кабинета при ширине 390px подтверждает, что мобильная страница больше не теряет кабинет: header, описание, 8-символьный ввод и основная CTA-кнопка помещаются без горизонтального скролла и остаются удобны для сенсорного ввода. Desktop screenshot также подтверждает сохранение общей визуальной системы MosaicVPN: сетка, serif-типографика, terracotta accent и hero-блок не конфликтуют с новой bento-подачей.

## Production-проверка

После развертывания `mosaic-bot.service` активен, а HTTP-проверки главной страницы, кабинета и новой админ-панели прошли успешно. Первое открытие кабинета в браузере показало закешированную старую страницу; открытие с cache-busting параметром подтвердило фактическую production-версию с новым интерфейсом и 8-символьным полем `/link`.

Публичная проверка также подтвердила новую bento-композицию раздела III и объясняющий блок раздела IV на `sub.zxc1x1.ru`. Новая страница `/admin.html` опубликована и без сессии показывает только безопасный вход через кабинет; никаких административных данных или контролов не раскрывается.

## Mobile fix: таблица протоколов

Исходная таблица использовала desktop-ширины трёх колонок, из-за чего статус обрезался на узком экране. Для ширин до 540px она теперь преобразуется в компактные строки: название протокола и транспорт расположены слева, а статус вынесен в отдельную правую колонку с фиксированной минимально необходимой шириной. Это исключает обрезание текста без горизонтального скролла.
