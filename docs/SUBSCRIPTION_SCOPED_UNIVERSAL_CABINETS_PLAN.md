# План: подписки с универсальными кабинетами и one-click подключение MosaicVPN

## Главная идея

Нужно убрать отдельную глобальную вкладку «Профиль/Аккаунт». В приложении главным объектом становится **подписка**: у неё есть маршруты, состояние обновления, собственная ссылка и, если сервис это позволяет, **кабинет именно этой подписки**. Пользователь не должен разбираться в технических сущностях `provider account`, `profile` или `manifest`.

> Пользователь видит: «это моя подписка MosaicVPN», «это рабочая подписка», «это ссылка из другого сервиса». Он открывает меню нужной подписки и управляет только тем, чем реально можно управлять у неё.

Таким образом, несколько сервисов и несколько аккаунтов одного сервиса выглядят как несколько самостоятельных подписок. Каждая может иметь свой кабинет, свою поддержку, свои устройства, свои платежи и собственную ротацию ссылки. Обычная внешняя URL-подписка остаётся нормальной подпиской, но без выдуманного «кабинета», пока пользователь не подключит его или сервис не раскроет свои возможности.

## 1. Новая модель объектов

### 1.1. Подписка — основной пользовательский объект

Любая запись в «Маршрутах» становится `SubscriptionWorkspace`.

| Поле | Назначение для пользователя | Технический источник |
|---|---|---|
| `id` | Устойчивый ID подписки на устройстве | Локальный UUID |
| `title` | «MosaicVPN», «Рабочий VPN», «Мои серверы» | Пользователь или сервис |
| `kind` | Сервисная, внешняя ссылка, локальная коллекция | `managed`, `external`, `local` |
| `routes` | Smart Groups и/или обычные серверы | Manifest/feed/local entries |
| `cabinet` | Состояние и возможности кабинета именно этой подписки | Описатель, полученный от сервиса |
| `connection` | Последний выбранный маршрут, статус, тесты | Локальное состояние |
| `order` | Порядок вкладок и списка | Локальное состояние |

`managed` — подписка, которую приложение получило через официальный поток входа или verified invite. `external` — URL/QR/файл, добавленный пользователем. `local` — сборник серверов, созданный вручную. На экране они отличаются небольшой подписью, но ведут себя одинаково как «подписки».

### 1.2. Кабинет — подключаемая возможность подписки

У `SubscriptionWorkspace` появляется необязательный `CabinetBinding`. Это не глобальный account, а привязка именно к подписке.

```text
CabinetBinding
  status                 unavailable | discoverable | connected | needs_reauth | error
  capability_level       basic | standard | full
  provider_id            проверенный ID сервиса, если есть
  issuer_origin          HTTPS origin кабинета
  credential_ref         ссылка на токен в OS secure storage
  account_subject        opaque ID у этого сервиса
  capabilities[]         баланс, freeze, devices, payments, rotate_link …
  last_sync_at
  public_summary         срок, трафик, статус, если доступно без полного кабинета
```

Подписка может существовать без `CabinetBinding`. Это нормальная ситуация: она просто работает как внешний источник маршрутов. После подключения кабинета та же подписка получает дополнительные действия, но не создаётся дубликат в списке.

### 1.3. Smart Groups и закрытый pool

У service-подписки Smart Groups находятся внутри её списка маршрутов наравне с VLESS/Trojan/прочими строками. Тип маршрута явно указан как «Smart Group», но он не является отдельной вкладкой и не вынесен в верхнюю навигацию.

Физические узлы private pool не попадают ни в строки маршрутов, ни в кабинет, ни в логи, ни в экспорт. Подписка получает только provider-managed manifest, candidate shard и итоговую конфигурацию для прямого подключения с устройства.

## 2. Как выглядят экраны

### 2.1. Dashboard

Dashboard содержит два последовательных выбора и не показывает два независимых способа подключиться:

1. **Подписка** — выпадающий список с названием и небольшим статусом: `MosaicVPN · активно`, `Рабочий VPN · 12 маршрутов`, `Мои серверы`.
2. **Маршрут** — Smart Group или сервер только внутри выбранной подписки.
3. **Подключить** — одна главная кнопка.

Если для подписки доступен кабинет, рядом с её названием есть сдержанный значок кабинета. Нажатие открывает кабинет этой подписки, а не отдельный общий экран.

### 2.2. Экран «Маршруты» / список подписок

Сверху — горизонтальные вкладки/чипы подписок с пролистыванием и drag-and-drop для пользовательских источников. Внутри выбранной подписки — список маршрутов. У каждой подписки есть меню `⋯` или контекстное меню.

| Действие меню | Когда показывается |
|---|---|
| `Открыть кабинет` | Кабинет уже подключён |
| `Подключить личный кабинет` | Cabinet discoverable, но ещё не подключён |
| `Проверить доступные сведения` | Для любой внешней URL-подписки |
| `Обновить` | Для удалённой подписки |
| `Переименовать` | External/local subscription |
| `Изменить порядок` | External/local subscription |
| `Удалить с устройства` | External/local subscription; service subscription удаляется через «Выйти из сервиса» |
| `Выйти из сервиса` | Managed subscription с подключённым кабинетом |

Кабинет помечается заметно, но спокойно: маленькая иконка «профиль/щит» и метка `Кабинет подключён` под названием подписки. Если подписка поддерживает подключение, но оно не выполнено, метка выглядит как `Доступен кабинет`.

### 2.3. Кабинет конкретной подписки

При открытии кабинета заголовок всегда содержит название подписки: `MosaicVPN · личный кабинет` или `Рабочий VPN · кабинет`.

Верхняя часть показывает доступ без лишней сложности: статус, срок/баланс, ссылку подписки и краткое количество устройств. Нижняя часть состоит только из доступных сервису действий. Например, MosaicVPN показывает пополнение, freeze, устройства, платежи, поддержку и ротацию ссылки. Другой сервис может показать только срок действия и кнопку сайта поддержки.

Не нужно показывать пустые карточки или «недоступно» для функций, которые сервис вообще не заявляет. Только возможности из verified `capabilities`.

## 3. Универсальный кабинет: три уровня

Не все сторонние подписки смогут сразу предоставить полноценный API. Поэтому кабинет должен деградировать честно, по уровням, а не исчезать или выдавать фальшивые данные.

| Уровень | Когда доступен | Что видно в приложении | Что можно сделать |
|---|---|---|---|
| **Базовый** | У приложения есть только subscription URL и parsed feed | Название, число маршрутов, последнее обновление, protocol mix, локальные тесты, возможный `expireAt` из subscription-info header/manifest | Обновить, проверить доступность, открыть исходную ссылку/сайт, управлять локально |
| **Стандартный** | Сервис публикует verified manifest или status endpoint | Срок, трафик, лимит устройств/квота, статус, ссылка на личный кабинет | Открыть кабинет в браузере, обновить, запросить re-auth |
| **Полный** | Пользователь выполнил auth, сервис поддерживает Mosaic Cabinet API | Баланс, биллинг, платежи, freeze, устройства, support, ротация ссылки, provider-defined actions | Все явно заявленные сервером действия прямо в приложении |

Базовый уровень — это не попытка «взломать» чужой кабинет. Клиент читает только открытый feed, подписочные заголовки и manifest, которые пользователь сам разрешил получить. Если срок отсутствует, UI честно пишет: `Сервис не передаёт срок действия в подписке`.

## 4. «Подключить личный кабинет подписки»

### 4.1. Контекстное действие для любой подписки

Пользователь открывает `⋯` у внешней или service-подписки и выбирает **«Подключить личный кабинет»**. Далее выполняется безопасный discovery flow:

1. Клиент показывает domain подписки и предупреждает, что кабинет будет подключён именно к этой подписке.
2. Если в URL или response есть verified discovery document (`/.well-known/mosaic-client.json` или явно указанный кабинетный manifest), проверяются HTTPS, schema version, `provider_id`, совпадение origin и допустимые endpoints.
3. Если вход поддержан, открывается provider-specific auth: сайт, pairing code, OAuth, email/password — но только тот, который сам провайдер описал в manifest.
4. После успеха сервис возвращает opaque credential, subject и привязку к существующей subscription `id`.
5. Подписка меняет метку на `Кабинет подключён`; её URL и маршруты не дублируются.

Если discovery недоступен, приложение предлагает не «ошибку», а два понятных действия: `Открыть сайт сервиса` и `Проверить доступные сведения`. External subscription остаётся рабочей.

### 4.2. Защита

Нельзя автоматически посылать subscription URL, ключи из share URI или токены на сторонний endpoint только потому, что он указан рядом. Подключение кабинета требует явного действия пользователя и строгой origin binding:

- endpoint кабинета обязан быть HTTPS;
- origin manifest должен совпадать с подтверждённым origin invitation/подписки либо быть явно подтверждён пользователем;
- токены хранятся per-subscription в OS secure storage;
- website callback переносит только одноразовый код и `state`/PKCE;
- сервис не получает информацию о других подписках пользователя;
- `Выйти из кабинета` не удаляет саму внешнюю подписку, если пользователь не выбрал это отдельно.

## 5. One-click подключение MosaicVPN с сайта

Для MosaicVPN нужен отдельный максимально простой путь: на сайте в кабинете пользователь нажимает **«Добавить MosaicVPN в приложение»**. Не нужно копировать ссылку, вводить `/link` или сначала создавать отдельный профиль.

### 5.1. Сценарий пользователя

1. Пользователь устанавливает приложение и открывает сайт MosaicVPN на том же телефоне/ПК.
2. В кабинете нажимает `Добавить в приложение`.
3. Сайт проверяет сессию. Если пользователь не вошёл — показывает существующий website-first login.
4. Сайт создаёт короткоживущий одноразовый **App Enrollment Code**, привязанный к session, устройству/`state`, client redirect и сроку жизни 5 минут.
5. Браузер открывает `mosaicvpn://enroll/callback?code=…&state=…`.
6. Приложение атомарно обменивает код на bootstrap response: provider metadata, subscription descriptor, direct credential, manifest, account capability summary и выбранный по умолчанию маршрут.
7. Приложение создаёт одну `managed` подписку `MosaicVPN`, сохраняет секреты и сразу показывает её на Dashboard. При возврате пользователь видит кнопку `Подключить`, а кабинет уже доступен в меню подписки.

На desktop используется такой же концепт, но callback возвращается в локальный loopback receiver или коду подтверждения в уже запущенное приложение. Внешняя ссылка не нужна и не отображается пользователю.

### 5.2. Идемпотентность

Если MosaicVPN уже добавлен, enrollment не создаёт дубликат. Он находит existing managed subscription по `provider_id + remote_subject_id`, обновляет токен/manifest и открывает эту подписку. Пользователь с несколькими реальными аккаунтами MosaicVPN может нажать `Добавить ещё один аккаунт`; тогда сайт явно спрашивает, какой аккаунт авторизуется, и создаётся отдельная подписка с понятным названием, например `MosaicVPN · личный` и `MosaicVPN · рабочий`.

## 6. Новые контракты данных

### 6.1. Client-side subscription record

```json
{
  "id": "sub_01J...",
  "title": "MosaicVPN · личный",
  "kind": "managed",
  "source_url": null,
  "provider": {
    "provider_id": "ru.mosaicvpn",
    "issuer_origin": "https://sub.zxc1x1.ru",
    "remote_subject_id": "opaque_subject",
    "cabinet_status": "connected",
    "capability_level": "full"
  },
  "catalog": {"id": "catalog_primary", "hide_physical_nodes": true},
  "last_selected_route": {"id": "smart-low-latency", "kind": "smart_group"}
}
```

### 6.2. Provider cabinet manifest

Provider manifest должен выдавать не только routes, но и понятное описание кабинета:

```json
{
  "schema_version": 1,
  "provider_id": "ru.mosaicvpn",
  "issuer_origin": "https://sub.zxc1x1.ru",
  "cabinet": {
    "supports_connection": true,
    "auth_methods": ["website_enrollment", "pairing_code"],
    "capabilities": ["status", "billing", "freeze", "payments", "devices", "subscription_link_rotation"],
    "endpoints": {"bootstrap": "/api/client/bootstrap", "account": "/api/account"}
  }
}
```

Клиент не выполняет ничего из manifest. Он использует только заранее известные endpoint types, валидирует schema и включает строго разрешённые UI actions.

## 7. Порядок реализации

| Очередь | Что делаем | Результат |
|---|---|---|
| 1 | Переименовать доменную модель в документации и коде: `SubscriptionWorkspace`, `CabinetBinding`, `CatalogKind` | Все новые изменения идут в правильную сторону, не плодятся profile tabs |
| 2 | Добавить per-subscription secure credential store и migration текущего MosaicVPN provider subscription | Нынешний пользователь не теряет доступ; кабинет закрепляется за одной MosaicVPN подпиской |
| 3 | Перенести Account UI из нижней вкладки в subscription cabinet sheet/page | Глобальная вкладка профиля исчезает; кабинет открывается через выбранную подписку |
| 4 | Реализовать Basic Cabinet parser: subscription-info headers, last update, route count, expiry если передан | Любая ссылка получает честный полезный обзор без сторонней авторизации |
| 5 | Реализовать `Connect Cabinet` discovery + verified manifest + auth binding | Сторонние совместимые сервисы получают стандартный/full cabinet без дубликатов |
| 6 | Добавить Mosaic `App Enrollment` endpoint и сайт-кнопку `Добавить в приложение` | Один клик добавляет подписку, кабинет и manifest в приложение |
| 7 | Переделать Android hosted facade и desktop daemon state с singleton Account на cabinet bindings по subscription ID | Несколько Mosaic/сторонних service subscriptions работают изолированно |
| 8 | Добавить UI/tests для multiple subscriptions, logout cabinet, rotation, unsupported provider и migration | Предсказуемая работа на Windows/Linux/Android |

## 8. Правила миграции текущего v0.3.15

Текущая service subscription `MosaicVPN` мигрирует в `SubscriptionWorkspace(kind: managed)` с тем же ID для совместимости. Ей создаётся `CabinetBinding(status: connected)` из существующего session/direct token. Smart Group manifest переносится к этому же workspace. Отдельная глобальная Account tab скрывается после того, как доступность кабинета в меню подписки подтверждена.

Импортированные URL-подписки мигрируют в `kind: external`, локальные сборники — в `kind: local`. Они не получают кабинет автоматически, но получают действие `Проверить доступные сведения`; при наличии verified provider metadata показывается `Подключить личный кабинет`.

## Итоговое решение, которое предлагается утвердить

```text
Подписка
├── маршруты
├── локальный статус подключения
├── тип: managed / external / local
└── необязательный кабинет этой подписки
    ├── basic: открытые сведения
    ├── standard: данные из verified manifest/status API
    └── full: авторизованное управление сервисом
```

Это сохраняет универсальность клиента, делает MosaicVPN onboarding максимально простым и не заставляет пользователя понимать различие между «профилем», «аккаунтом» и «подпиской». При этом технически несколько разных аккаунтов и операторов остаются полностью изолированными.
