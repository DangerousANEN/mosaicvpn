# v0.3.24: Subscription-Scoped Cabinet Binding Contract

## Product invariant

A stored subscription URL is independently usable for refresh, route discovery, Smart Group selection, connection and deletion. A cabinet binding is an **optional, device-local capability attachment** to exactly one subscription ID. It must never change the subscription `source`, never make the URL immutable, and never be required by a VPN connection path.

## Binding record

Every binding is keyed by the client-local `subscription_id` and contains the provider identity, account identity, subscription URL at the time of binding, a cabinet session token, the opaque direct token, a non-secret display username and binding timestamp. Tokens stay in secure storage on mobile and in the local daemon state on desktop; server responses never list another binding's credentials.

| Field | Purpose | Exposure |
|---|---|---|
| `subscription_id` | Binds one cabinet capability to one local URL source | Local client state only |
| `provider_id` | Declares the compatible provider adapter | UI capability check only |
| `provider_account_id` | Opaque provider account discriminator | Local client state only |
| `subscription_url` | Detects replacement or link rotation | UI and local state |
| `session_token` | Authorizes cabinet operations | Secure/local protected storage only |
| `direct_token` | Identifies the provider feed returned at authorization | Secure/local protected storage only |
| `username` | Non-secret display identity | Cabinet UI only |

## One-time attachment flows

The website and manual code flows issue the same short-lived, single-use authorization material. The callback flow additionally binds local state through an unguessable `state` value. The manual flow accepts the existing 8-symbol code grammar, burns the code atomically and returns the subscription URL plus cabinet credentials. In both cases the client first resolves or creates the subscription URL row and only then persists the binding against its local ID.

## Compatibility migration

Existing global Mosaic account material migrates only if the device has exactly one compatible Mosaic URL subscription. If there are zero or multiple compatible sources, the legacy session remains available only for migration recovery and no automatic attachment occurs. A subscription deletion also deletes its local binding. Link rotation updates the matching binding's URL and preserves the local subscription ID where the provider returns a replacement URL.

## Cabinet API rule

Every authenticated cabinet operation receives the selected binding. UI data providers are families keyed by `subscription_id`; no profile, payment or control screen may query a global application account as a substitute for the selected source.

## Acceptance checks

1. Importing and connecting a Mosaic URL works with no binding.
2. A website callback reuses an existing matching URL row and attaches its cabinet only to that row.
3. A valid 8-symbol website or Telegram code attaches to the selected compatible URL row.
4. Deleting a source deletes its binding and does not alter any other source.
5. Two Mosaic URL sources can be bound to different accounts on one device without cross-reading cabinet data.
6. Base subscription metadata remains visible without a binding; balance, payments, devices, freeze and link rotation appear only after a binding exists.
